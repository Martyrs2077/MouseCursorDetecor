## 提交并推送

用户说“推送到 GitHub”时，默认包含检查、提交本次相关改动和推送。

1. 阅读相关 diff 和新文件，确定本次任务的提交范围。存在来源或归属不明的
   已有改动、预先暂存内容或待推送提交时，先说明并询问，不把它们顺带发布。
2. 执行项目允许且与改动相称的静态检查，核实文档同步情况。向用户简要展示
   待提交文件范围和提交说明，再按已获得的推送授权继续。
3. 使用明确文件路径暂存，不用 `git add .`、`git add -A` 或 `git commit -a`。
   检查 staged diff 与文件清单，确保没有混入预先暂存的无关内容；无法安全分离
   时先询问，不擅自取消用户原有暂存。提交说明简洁描述实际改动。
4. 没有待提交改动时不创建空提交；已有本次相关提交可直接进入推送检查。
   使用单次配置提供提交身份，例如 `git -c user.name=Martyrs2077
   -c user.email=Martyrs2077@outlook.com commit`，执行时作为同一条命令传参。
5. Fetch 后比较本地与远端提交关系。远端已领先或双方分叉时，保留本地结果并
   报告，不自动 pull、merge 或 rebase。完全一致则报告无需推送。
6. 确认目标及待发布提交后，用明确 refspec 将当前已核实的 `Dev` 推送到
   `refs/heads/Dev`，不附带 tags、其他分支或 mirror。例如：
   `git push origin HEAD:refs/heads/Dev`，其中 `origin` 必须是已核实的 remote。
   设置 upstream 仅限已确认的 `Dev` 映射，不覆盖不匹配的跟踪关系。
7. 推送后读取远端 `refs/heads/Dev`，核对与本地提交哈希一致。
   被拒绝时不改用 force；返回不明确时先核实远端再决定是否重试。

## 拉取更新

用户说“拉取更新”时，默认只执行快进更新，不自动提交或推送本地改动。

1. 确认工作区、索引和当前分支满足同步条件。存在未提交改动时可先 fetch
   获取信息，但先询问如何处理本地改动，再更改工作区；不自动 stash 或丢弃。
2. Fetch 已确认远端的 `Dev`，检查 incoming diff、文件路径及提交关系。
3. 相同提交：报告已是最新。仅本地领先：报告没有远端更新及领先数量，不推送。
   仅远端领先且保护检查通过：对已 fetch 的目标执行 `merge --ff-only`。
   双方分叉或历史无关：停止，展示提交差异并请用户选择后续处理。
4. `--ff-only` 失败时不降级成普通 merge、rebase 或强制重置。
   用户另行授权处理冲突时再操作，保留其改动并遵守构建限制。
5. 更新后核对 HEAD、目标提交及工作区状态；不自动构建或启动程序。
